# Inventory Management System (FastAPI + React + PostgreSQL)

A full-stack CRUD inventory management application — a FastAPI backend with PostgreSQL persistence, consumed by a React frontend. Built to go beyond tutorial-following and implement a real, working system: REST API design, ORM-based database access, request validation, environment-based configuration, and proper HTTP error handling.

## Overview

This project is a CRUD inventory/product management system with a FastAPI REST API backend, a PostgreSQL database accessed through SQLAlchemy, and a React frontend. It was built hands-on to understand — not just copy — how a backend service is structured end-to-end: schema design, ORM models, request/response validation, dependency-injected database sessions, environment-based secrets management, and REST-compliant error handling.

## Tech Stack

**Backend**
- [FastAPI](https://fastapi.tiangolo.com/) — Python web framework
- Uvicorn — ASGI server
- SQLAlchemy — ORM for PostgreSQL access
- Pydantic — request/response schema validation
- psycopg2 — PostgreSQL driver
- python-dotenv — environment-based configuration

**Database**
- PostgreSQL

**Frontend**
- React

**Tooling**
- Git & GitHub — version control
- Pyright — static type checking

## Architecture

| File | Responsibility |
|---|---|
| `models.py` | Pydantic schemas — the API's request/response contract |
| `database_models.py` | SQLAlchemy ORM models — actual database table structure |
| `database.py` | DB engine/session setup, reads config from environment variables |
| `main.py` | FastAPI app, route handlers, dependency-injected DB sessions |
| `frontend/` | React application consuming the API |

Schema (`models.py`) is kept separate from the ORM model (`database_models.py`) so the API's public contract can evolve independently of the database's internal structure.

## API Endpoints

| Method | Endpoint | Description |
|---|---|---|
| GET | `/` | Health check |
| GET | `/products` | List all products |
| GET | `/product/{id}` | Get a single product by ID (404 if not found) |
| POST | `/products` | Create a new product |
| PUT | `/products/{id}` | Update an existing product (404 if not found) |
| DELETE | `/products/{id}` | Delete a product (404 if not found) |

Interactive API docs (Swagger UI) are auto-generated by FastAPI and served at `/docs`.

## How to Run

### Backend
```bash
# 1. Clone the repository
git clone https://github.com/gitvorks/inventory-management-crud-fastapi-react-postgresql.git
cd inventory-management-crud-fastapi-react-postgresql

# 2. Create and activate a virtual environment
python -m venv .venv
source .venv/bin/activate   # Windows: .venv\Scripts\activate

# 3. Install dependencies
pip install -r requirements.txt

# 4. Configure environment variables
# Create a .env file in the project root:
#   DATABASE_URL=postgresql://<user>:<password>@localhost:5432/<db_name>
# This file is git-ignored and must be created locally — no credentials
# are stored in the repository.

# 5. Ensure PostgreSQL is running and the target database exists

# 6. Start the server
uvicorn scripts.main:app --reload

# API:  http://127.0.0.1:8000
# Docs: http://127.0.0.1:8000/docs
```

### Frontend
```bash
cd frontend
npm install
npm start
```

## Security & Engineering Notes

Documented transparently as part of the build process, not hidden:

- **Credentials management:** database configuration is read from environment variables via `python-dotenv`, never hardcoded. An earlier version of this project had a hardcoded connection string in source; it was identified, removed, and the credential was rotated.
- **Error handling:** all "not found" cases raise `HTTPException` with a `404` status code rather than returning ambiguous `200 OK` responses with error strings — clients can reliably distinguish success from failure by status code, per REST conventions.
- **Data integrity fix:** the initial database-seeding logic had a bug where an empty-check (`.count`) was missing a method call (`.count()`), so it always evaluated as truthy. Identified and fixed during testing.

## Known Limitations & Future Improvements

- [ ] `POST /products` currently accepts a client-supplied `id` rather than relying on database auto-generation. This is a known trade-off — flagged for a future revision to enforce server-generated primary keys.
- [ ] No input constraints yet on numeric fields (e.g. negative price/quantity should be rejected via Pydantic validators)
- [ ] No automated tests (pytest) for the API layer
- [ ] No pagination on `GET /products`
- [ ] Not yet containerized (Docker) or deployed
